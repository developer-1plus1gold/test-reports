/**
 * Cron: marketing publisher dispatcher.
 *
 * Every 5 minutes — finds pieces where status='scheduled' AND
 * scheduled_at <= now() AND no published_at yet, and dispatches the
 * marketing-publisher agent for each. Publisher itself handles the
 * per-channel API calls + state transitions.
 *
 * Scheduled via vercel.json `*​/5 * * * *`.
 *
 * ⚠️ A REFUSED PUBLISH IS A LOUD EVENT (2026-09-02). This cron used to be
 * entirely silent: it wrote no `cron_runs` heartbeat, sent no alert, filed no
 * decision, and kept only `HTTP ${status}` from the dispatch — throwing away
 * the response body that names the failing gate. Drumbeat piece `b0ea1213` was
 * consequently blocked for 28 hours across ~340 rejected retries with nothing
 * to show for it, because its video asset had never been operator-approved.
 * "Blocked forever" and "nothing due" looked identical from outside. Now every
 * tick leaves a heartbeat, and a blocked piece pages once per (piece, blocker).
 * See src/lib/marketing/publish-failure.ts for the reasoning.
 *
 * ⚠️ AND A PIECE CAN BE STUCK WITHOUT BEING BLOCKED (2026-09-03). `whatsapp_status`
 * has no publishing API: the publisher prepares it, marks it `manual-pending-…`,
 * fires ONE "manual post needed" alert, and waits. `published_at` only lands
 * when the operator confirms — so the due predicate below stayed true forever
 * and this cron re-dispatched the piece every 5 minutes, publishing nothing
 * (every channel idempotency-skipped), filing a junk `notify` decision each
 * time, and reporting `published=1` on a green heartbeat. Piece b0ea1213 did
 * that 26 times in two hours. Now such a piece is NOT dispatched, is counted as
 * `awaiting_manual` rather than `published`, and is re-nudged daily after six
 * hours so a missed one-shot alert cannot strand it silently.
 */
