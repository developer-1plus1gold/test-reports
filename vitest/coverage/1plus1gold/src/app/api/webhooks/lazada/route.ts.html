/**
 * POST /api/webhooks/lazada — Lazada Push (step 2c part 2, docs/lazada-integration-design.md §3).
 *
 * Set as the Push URL in the Lazada app console. Lazada signs each message with
 * HMAC-SHA256(app secret, app key + raw body) in the `Authorization` header (hex) and
 * retries unless we answer 200 quickly — so we verify, record, ack, and do the work after
 * the response (waitUntil).
 *
 * The message is only a NUDGE: on a trade-order message (message_type 0) we run the same
 * idempotent order import the 10-minute cron runs (syncLazadaOrders, which itself honours
 * the import switch). Nothing in the body is trusted beyond "something changed" — the
 * import reads the order back from Lazada's authenticated API — so a forged message can at
 * worst cause one extra poll, and an unsigned one does nothing at all.
 *
 * A REVERSE-order message (message_type 10) carrying a cancel request (reverse_status
 * CANCEL_INIT…) is applied to the order's import row as a `cancel_requested` issue — a signed
 * message, so its body is Lazada's own word — and alerts the admins once
 * (lib/marketplace/cancel-request.ts, 2026-11-20). Lazada leaves the order ready_to_ship until
 * the seller accepts the request, so the order poll alone never sees it.
 *
 * Every message (signed or not) lands in `marketplace_webhook_captures` (30-day retention),
 * so the first real one proves the signature format. ▶ Until it has, a signature mismatch is
 * the FIRST thing to check: the 10-minute poll keeps importing either way.
 */
