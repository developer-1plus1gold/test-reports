// ─────────────────────────────────────────────────────────────────────────
// split-invoice — pure logic for rendering ONE order's invoice as MULTIPLE
// distributed invoices (admin-only, exception-basis). This is a RENDER-only
// feature: it constructs several ReceiptData objects from one order and the
// operator's split plan; the same generateReceiptPdf/ReceiptPage renders each.
// Nothing about how the order was created, paid, or booked changes.
//
// Two mechanisms in one plan model:
//   • split a qty>1 line into multiple invoices (5× → 5 invoices), and/or
//   • put different lines on separate invoices.
// A plan is a list of GROUPS; each group is a list of SLICES {orderItemId, qty}.
//
// INVARIANT (money always reconciles): every unit of every line must be
// assigned to exactly one group (full coverage, no over/under-assignment), so
// the split set is an exact re-presentation of the order. `validateSplitPlan`
// enforces it.
//
// Non-merchandise (shipping / processing fee / promo & referral discounts):
//   • "merchandise_only" (default): split pages carry NONE — the master invoice
//     (page 1) holds them. Each split's grand total = its merchandise subtotal.
//   • "proportional": each charge is apportioned across groups by merchandise-
//     VALUE share, with the rounding residual assigned to the LAST group so the
//     apportioned amounts sum EXACTLY to the order's. We distribute the order's
//     ACTUAL amounts — never recompute — so the splits always tie back.
// (GST: the business is not GST-registered — BUSINESS_CONFIG.gst.isRegistered=
//  false — so there is no separate GST amount to apportion; per-item IPM/taxable
//  badges are informational and carried on each split automatically.)
// ─────────────────────────────────────────────────────────────────────────
