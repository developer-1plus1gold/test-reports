/**
 * GET /api/cron/retention-anonymise-accounts  (PDPA Phase 2+3 / R1 + R2)
 *
 * Daily. Anonymises accounts that have crossed a retention window
 * (content/governance/pdpa-retention-schedule.html):
 *   • R2 — never transacted, inactive > 24 months (no AML hold)
 *   • R1 — transacting, LAST order older than the 5-yr PSPM/MinLaw AML window
 *
 * Eligibility is the pure classifier (selectAccountRetention); the actual scrub
 * is the shared anonymiseAccount() — the SAME code the self-service delete route
 * runs — so nothing drifts. Between "eligible" and "anonymised" sits a pure,
 * tested exclusion gate (filterAnonymisationTargets): internal/demo, house
 * (external-channel) customers, ADMIN_TEAM operators, and already-anonymised
 * accounts are never touched. Every anonymisation is recorded in
 * data_retention_log. The orchestration lives in
 * src/lib/governance/retention-run.ts (a route.ts may only export handlers).
 *
 * At launch (mid-2026) nothing is eligible — the oldest account is months old,
 * so R2's first crossing is ~2028 and R1's ~2031. The cron no-ops until then,
 * then enforces the window daily. PROD-only + GET=POST (Vercel Cron uses GET).
 */
