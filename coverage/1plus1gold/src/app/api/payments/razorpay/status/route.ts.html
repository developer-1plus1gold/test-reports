 *
 * Polled by /payment/confirming after Razorpay redirects back. Same protocol
 * as /api/payments/hitpay/status: completed | processing | stalled | failed | pending.
 *

 *   check_hitpay=1): if the row is still pending, ask Razorpay's API and
 *   complete the order through the shared atomic claim. The callback query
 *   string is never trusted on its own.
 *
 *   Abandoned (HitPay parity, 2026-10-29): a customer who closes Razorpay's page
 *   leaves the link `created` with no payment attempt, and Razorpay never marks
 *   it — so the poll read "pending" until the link expired and the confirming
 *   screen hung. check=1 is only sent once the customer has RETURNED (web
 *   confirming page; iOS after the payment sheet closes or redirects back), so an
 *   attempt-free open link then means they did not pay: report `failed` /
 *   `abandoned`, exactly as HitPay's requires_payment_method rule does. Like
 *   HitPay, the row and the link are left open — a payment that lands late still
 *   completes through the webhook or the reconcile cron.
